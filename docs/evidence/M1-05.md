## 2. The reachability test proves that `suggest_urgency` needs `run_rules`

- **Static check.** `test_suggest_urgency_is_unreachable_without_run_rules` removes every edge touching `run_rules` from `graph.get_graph().edges`, then walks the graph from START.
  - With `run_rules`, `suggest_urgency` is reachable; without it, it is not.
  - The only edge into `suggest_urgency` comes from `run_rules`.
  - Because the conditional edges have path maps, `get_graph()` lists every possible edge.
- **Nurse review guard.** `test_nothing_after_the_nurse_review_is_reachable_without_it` does the same for `nurse_review`. Without it, `assign_token`, `writeback`, `build_briefing` and END are all unreachable.
- **Runtime check.** In `test_rules_run_on_the_final_facts_before_the_suggestion`:
  - `node_trace` shows `run_rules` immediately before the only `suggest_urgency`;
  - the urgency model received exactly the `StructuredFacts` that the rules evaluated last.

A full run's trace:

```
identify, fetch_ehr_context, ask, await_answer, extract, run_rules, ask, await_answer, extract, run_rules,
ask, await_answer, extract, run_rules, ask, run_rules, suggest_urgency, nurse_review, assign_token, writeback,
build_briefing
```

**Mutation check.** Adding an `ask → suggest_urgency` path to the graph makes the reachability test fail.

## 3. The graph pauses at `nurse_review` and resumes with confirm, and with override + reason; override without a reason is rejected

`test_interrupts.py` drives the scripted answers through raw `Command(resume=...)` and checks each `__interrupt__` value along the way. Interrupts surface as `result["__interrupt__"]`, a list of `Interrupt(value, id)`, checked against the pinned LangGraph (ADR-020).

- **The pause.** The graph stops at `{"kind": "nurse_review", "suggestion": ..., "alerts": [CHEST_PAIN_ECG_10MIN], ...}`. Nothing after the review has run yet: no token, and no `assign_token` in the trace.
- **Confirm.** The graph reaches END (`next == ()`) with token `A001` and room `triage-1`, writeback `stubbed`, and a briefing reference. The queue is called at the suggested level. The events are `alert.raised`, `triage.suggested`, `triage.confirmed` and `intake.completed`, once each.
- **Override with a reason.** OVERRIDE to level 2 with `clinical_judgement` and a note stores the new level, the reason code and the note. The queue is called at level 2, and `triage.confirmed` carries `final_level` 2.
- **Override without a reason.** `decide()` raises `InvalidNurseDecision` ("OVERRIDE needs an override_reason_code"). The graph is still at `nurse_review` and no decision is stored. A later valid OVERRIDE with a reason reaches END.
- **Other rejected decisions** (6 cases):
  - a changed level without a reason;
  - another session;
  - a stale suggestion id;
  - the wrong scale;
  - "other" without a note;
  - level 7.
- **A raw invalid resume** that bypasses `decide()` pauses again, with `error` naming the missing reason. The node never raises: a node that raises after `interrupt()` replays the same invalid value on every resume in LangGraph 1.2.12 (ADR-020). A later `decide()` goes through.
- **Patient answers.** An empty answer raises `InvalidAnswer` from `answer()`. As a raw resume, it asks the same question again with `error`, and the next valid answer continues.
- **No suggestion.** If the model cannot suggest (a stub `NoSuggestion`), the review shows `suggestion: null` with the reason. The nurse sets level 2, and no `triage.suggested` event is sent.

**Mutation check.** Removing the "changed level needs a reason" check makes a test fail.

## 4. The restart test passes against Postgres

`test_resume_after_restart`, on a throwaway `careflow_intake_test` database with the checkpoint tables created by `setup_postgres`:

1. The graph runs to `nurse_review` with `AsyncPostgresSaver`, and the saver's connection is closed.
2. A new saver, new ports and a new graph are built on the same database, and the same `thread_id` is read back. It is still waiting at `nurse_review`. The restored facts are `FactEntry`, the alerts are `Alert`, and the suggestion equals the one before the restart. So the strict serializer rebuilt every type.
3. `decide()` reaches END with token `A001`. After the restart only `triage.confirmed` and `intake.completed` fire, on the new ports; the old ports saw only `alert.raised` and `triage.suggested`.

## 5. The 8-turn cap sets `intake_truncated`

- **Turn cap.** `test_an_endless_conversation_stops_after_8_turns`: a conversation that never ends stops after exactly 8 patient turns (`turn_count` 8). `flags.intake_truncated` is true, and the nurse review shows it.
- **Time cap.** `test_the_conversation_stops_after_120_seconds`: with a clock that advances 15 s per read, the conversation stops before 8 turns, once 120 s have passed.
- **No false flag.** A scripted conversation that completes is not flagged.

## Deviations from the issue text

- **Invalid input pauses the node again.** Where the issue says `nurse_review` raises, it calls `interrupt()` again with the error. `decide()` and `answer()` raise `InvalidNurseDecision` or `InvalidAnswer` before resuming. In LangGraph 1.2.12, raising inside the node after `interrupt()` replays the invalid value on every later resume, and that would break "a later valid resume still succeeds".
- **`FactEntry {key, fact}` instead of a bare `Fact`.** The contracts' facts carry no key.
- **Extra state fields:** `language`, `started_at`, `conversation_complete` and `suggestion_unavailable`.
- **Where the cap decision is made.** `run_rules` sets `intake_truncated`, and `route_after_rules` only reads it, because a LangGraph router cannot write state.
- **Its own test database.** The restart test uses `careflow_intake_test`, not `careflow_test`, because the API suite drops and recreates `careflow_test` in the same pytest run.
- **Port signatures follow the later issues.** `Extractor.extract(turns, existing_facts, question_keys) -> ExtractionResult` matches M1-06, and `Question.source` matches M1-07, so those issues plug in without changing the graph.
- **`NurseDecision` fields.** The contract's names are used: `action` CONFIRM/OVERRIDE, `final_level`, `override_reason_code` plus `override_note`, and `nurse_user_id`.
