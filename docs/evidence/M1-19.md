# M1-19: one-command start and the three journeys on the real stack

Status: 27 September 2026, SHE-315. Every run below is on this Mac (Apple silicon, 18 GiB),
against the real API, Postgres, Valkey and HAPI FHIR started by `make up`, with the seven
synthetic personas. Research prototype; synthetic data only; not for clinical use. Design:
ADR-047 (builds on ADR-046's isolated stacks).

The runs use the isolated test stack `careflow-test` (every port +10000) and, for the
fresh-clone check, a third stack `careflow-verify` (+20000). The owner's dev stack (`careflow`,
5432/6379/8080) kept running throughout and was never stopped.

## What changed

- `make up`/`make down` run any named stack (`CAREFLOW_STACK`, `CAREFLOW_PORT_OFFSET`) with its
  own ports, pidfile, log and Procfile, and stop only what this checkout started. `make up`
  returns only when the API reports its database, Valkey and FHIR server as "ok".
  `careflow-test` now defaults to +10000 in `make up` too (it used to get offset 0, the dev
  stack's ports, when `CAREFLOW_PORT_OFFSET` was unset).
- `LOCAL_LLM=1` starts the model through `scripts/with_llm.sh`; the server stops with the
  stack (checked below). The API's graceful shutdown is bounded to 3 s: before, `make down`
  SIGKILLed it while the simulated vitals stream was still running.
- The root `e2e/` package: `chest-pain.spec.ts`, `routine.spec.ts`, `sepsis.spec.ts`; `make e2e`
  runs them (the apps' Prism smoke tests moved to `make e2e-apps`). Model replies are replayed
  from `e2e/replays/providers.cassette.json` (8 extraction replies recorded from the local
  Qwen3.5-9B), or live with `E2E_LIVE=1`.
- `packages/providers/tests/test_one_line_switch.py`: the provider switch is one line.
- A CI `e2e` job (pushes to `main`, PRs labelled `e2e`, on demand) and the README quick start.

### Bugs the journeys found, fixed here

1. **Alerts were stamped with a fixed stub clock.** `build_real_ports` took the stubs'
   `SteppingClock` (09:00:00Z, one second per call), so `raised_at`, fact and suggestion times
   were fiction. It now defaults to the real UTC clock
   (`test_real_ports_read_the_real_clock`; the flow test asserts arrival <= `raised_at` <= now).
2. **A re-raised alert took each evaluation's time.** Every turn re-runs the rules, and the
   reducer replaced the alert whole, so `raised_at` drifted to the latest turn while
   `alert.raised` had gone out once, at the first. The briefing ("raised N min after arrival"),
   the FHIR Flag's `period.start` and the Task's `authoredOn` inherited the drift. The reducer
   now keeps the first raise and takes the rest (evidence, partial, text) from the new
   evaluation. `test_a_re_raised_alert_keeps_its_first_raise_time_and_takes_the_new_content`
   and the flow test (the ECG alert's time unchanged after the nurse's vitals re-run the rules)
   both fail without the fix and pass with it.
3. **The first latency figures were wrong, and are not used.** A recording run reported "on the
   nurse's worklist −213 ms after the patient sent it" (bug 2), and the next runs "+1 ms":
   the worklist locator matched a chest-pain row left by an earlier run. The chip is now read
   from this session's row (`tr[data-session=…]`), and every figure below comes after both
   fixes.
4. Back-to-back runs hit the API's login limit (5 a minute): Playwright empties `test-results/`
   at the start of each run, where the staff tokens were cached. They are now reused from
   `.run/e2e/` (git-ignored, mode 0600). The limit is unchanged.

## What each journey asserts

- **Chest pain** (persona 100001; simulated device `normal`). The nurse signs in through the
  staff login page. The `CHEST_PAIN_ECG_10MIN` chip appears on this session's row of the open
  worklist within 2 s of the answer to the turn that raised it (the complaint, in every run; the
  2 s budget is asserted on this machine and reported on a CI runner, docs/FLAKY.md). No token
  before the nurse decides. The session card shows the ECG banner
  with a countdown; "ECG done" stops it (unchanged 2 s later). The nurse decides; the kiosk and
  the nurse's result show the same token; a second decision is refused (409); the API's session
  token and the public board (read by the board device) show that token once. The nurse calls
  the patient in and the kiosk shows the room. The doctor's briefing has a chest-pain item whose
  source popover marks the patient's own words. HAPI: one Encounter
  (`identifier=urn:careflow:session|{id}`) with priority `KTAS-{level}`, one Flag, one Task
  with `restriction.period.end` and status `completed`, vitals Observations, one
  QuestionnaireResponse and one document Bundle.
- **Routine walk-in** (100005, "I twisted my ankle playing football yesterday"). No alert
  banner and no token before the nurse; a decision sent with the kiosk device's token or the
  patient's token is refused (403); the nurse overrides the level with a coded reason; the kiosk
  shows a token; HAPI's Encounter priority is the nurse's level and there is no Flag.
- **Sepsis** (100004, fever and shivering; simulated device `septic`). The kiosk's partial
  NEWS2 raises the "Possible sepsis (NEWS2)" banner marked "Partial NEWS2"; the nurse enters RR
  24, SBP 95, Alert, no oxygen; the NEWS2 summary shows the full score with no partial badge;
  the nurse decides; the kiosk shows a token; HAPI has one NEWS2 total Observation (SNOMED
  1104051000000101), status `final`, and a Flag.

## Latency, measured (never a gate)

"Raised" is the alert's `raised_at` (the server's clock) minus the moment the test sent the
turn; "on the worklist" is when the chip rendered on the nurse's open worklist. One machine, one
clock. CONVENTIONS' target is alert p95 <= 1000 ms; three samples give no p95, so the samples
are listed.

| Mode | Alert raised after the send | On the worklist after the send | After the kiosk got the answer | Raised → worklist |
| --- | --- | --- | --- | --- |
| Replay, run 1 | 61 ms | 781 ms | 692 ms | 720 ms |
| Replay, run 2 | 62 ms | 782 ms | 689 ms | 720 ms |
| Replay, run 3 | 54 ms | 1,297 ms | 1,215 ms | 1,243 ms |
| Local model, final journeys | 18,241 ms | 19,385 ms | 1,109 ms | 1,144 ms |
| Local model, earlier journeys, run 1 (new server) | 18,149 ms | 18,998 ms | 795 ms | 849 ms |
| Local model, earlier journeys, run 2 (same server) | 6,420 ms | 7,824 ms | 1,380 ms | 1,404 ms |

- From the alert's raise to the nurse's screen took 720 to 1,404 ms; measured that way, three
  of the six samples are over the 1000 ms target. The steady ~720 ms in replay comes after the
  rules have raised the alert (the event, its delivery to the open worklist and the redraw).
  M2-07 (live refresh) and M6-01 (performance) own it.
- With the local model, the model's reading of the complaint dominates: the first model-backed
  turn after the model server starts took 18.1 to 18.3 s (a short warm-up request does not warm
  the extraction prompt); on a server that had already served a run, 6.4 s.

| The provider-switch test passes, with a 1-line diff | 2 passed; the diff is exactly the `extraction:` line |
| `docker stats --no-stream` total <= 6 GB | 2.90 GiB with the dev stack and the fresh clone's; 3.25 GiB with the dev and test stacks |
| The CI `e2e` job is green; the quick start works on a fresh checkout without port clashes | CI: see "CI" below (green). Fresh checkout: on +20000 beside the running dev stack, no clash |

The handoff's further checks: nurse-only finalization (a kiosk or patient decision is refused,
403; no token before the nurse decides), provenance (the patient's own words marked in the
doctor's source popover), the ECG Task completed, the full NEWS2 after the nurse's vitals, one
queue assignment (a second decision 409; one token on the kiosk, the nurse's card, the API and
the board), idempotent FHIR resources (one Encounter, Flag, Task, QuestionnaireResponse and
Bundle per session), deterministic replay with a retained local-model run, readiness that
checks the API's dependencies, and the local model only through `scripts/with_llm.sh`.
