# M2-06: the QR hand-over from the kiosk to the patient's phone, verified

Status: 27 September 2026, SHE-300. The core (ADR-037) and the phone's reload recovery (ADR-044,
PR #38) were merged earlier; this change adds the missing security tests and the two-device
journey on the real stack, and fixes what they and the handoff found (ADR-048). Research
prototype; synthetic personas only; not for clinical use.

## What changed

- **A lost answer to a successful claim is recoverable, by the claiming phone only.** The phone
  sends a random `claim_key` with each code; the claim keeps its SHA-256. The same code with the
  same key, while the code is valid, gets a new phone credential for the same session; any other
  replay is still 409.
- **A second hand-over after the 2-hour Redis mark is refused.** The graph's `channel` now blocks
  issuing and claiming another code once the session is on the phone. Before, once the mark
  expired, another code of the same session could be claimed.
- **Phone tokens renew** (`POST /v1/sessions/{id}/renew`): a still-valid phone token swaps for a
  new 30-minute one while the visit is open, at most 12 hours after check-in; a kiosk token or a
  device gets 403, an expired or revoked token 401. The companion renews 10 minutes before expiry
  and when the phone wakes, and every API call uses the latest token.
- **The kiosk forgets a handed-over patient however it learns of it.** It keeps listening after
  the patient closes the code panel, and any 401 on the patient's calls wipes the patient and
  returns to the welcome screen.
- **A real phone can reach the stack** with `CAREFLOW_PUBLIC_HOST=<LAN address> make up` (the QR
  link, the phone's API address, CORS and the API's listening address); off by default.
- The real-stack test client moved to `services/api/tests/conftest.py` (`flow`), shared by the
  flow and hand-over tests; `e2e/` gained the phone helpers and a request capture.

## The two-device journeys

`e2e/journeys/qr-handover.spec.ts`: the kiosk and a phone (a second browser context with
Playwright's Pixel 7 profile) on the real API, Postgres, Valkey and HAPI, persona `qr-phone`
(100006). The answers are the routine walk-in's, so the model replies are the recorded ones: the
extraction prompt holds only the conversation.

1. **The hand-over.** Two answers on the kiosk; "Continue on your phone"; the phone opens
   `{companion}/claim#t=<code>` (the value in the QR image, read from the kiosk's own `POST /qr`
   answer, as a camera would). The phone shows question three and clears the fragment; the kiosk
   shows "Continued on your phone" and is back on the welcome screen within 6 s, with only its own
   sign-in and simulator setting in sessionStorage (no session id, no patient token); the kiosk's
   patient token gets 401. A phone reload keeps question three; the phone finishes the intake.
   The capture of every request of both browsers: the code appears in exactly one request, the
   claim's POST body, and in no URL.
2. **A lost claim answer.** The claim reaches the API (200) but its answer is dropped; the phone
   shows "We could not reach the clinic"; the kiosk forgets the patient; a second phone sending the
   code with its own key gets 409; "Try again" sends the same code and key and the phone gets its
   question. The capture shows both claims with the same key and the code in no URL.
3. **A lost answer to a turn, and a stale answer.** The phone's answer reaches the API but its
   response is dropped; the phone reads the server's checkpoint instead of sending again (one
   `POST /turns`), and shows the next question; an answer carrying the old revision gets 409 and
   changes nothing.

Three consecutive runs of all journeys (M1-19's three and these three), replayed models, stack
`careflow-e2e` (+30000) from a worktree of this branch beside the running dev stack:

## Not run

- **A physical phone scanning the kiosk's code.** No phone was available to this run, and binding
  the API to the LAN on this Mac (firewall on) may raise the system's "accept incoming
  connections" prompt, which is the owner's decision. The address plumbing is covered by
  `scripts/tests/test_stack.py` (the QR link, the API address, CORS and the listening address with
  and without `CAREFLOW_PUBLIC_HOST`); the owner can run
  `CAREFLOW_PUBLIC_HOST=<LAN address> make up` and scan the code.
- **Voice on the phone.** Not built (ADR-037); text and taps only.

Handoff items: the lost-claim case is recovered securely and explicitly (the claiming phone's key,
journey 2); reachable origins are configurable (`CAREFLOW_PUBLIC_HOST`; a physical phone not run);
API-unavailable recovery (journey 2's network error, PR #38's tests); duplicate answers and
revision conflicts (journey 3); reconnect snapshot refresh (journey 1's reload); terminal status
(PR #38's tests; a renewal refused for an ended visit clears the phone); bounded renewal that
never revives a kiosk or hand-over credential (the renewal tests).
