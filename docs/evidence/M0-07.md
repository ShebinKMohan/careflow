## 3. Cross-clinic: a clinic-A token sees 0 clinic-B rows, and a clinic-B insert fails

The tests create their own two clinics, each with one `patient_session` row. They connect as `careflow_app`, the API's runtime role.

- `test_a_clinic_a_token_through_get_db_sees_and_writes_only_clinic_a` covers the full request path: clinic-A JWT → `get_principal()` → `get_db()` (sets `app.clinic_id`) → RLS. Through a probe route, clinic A has 1 row and clinic B has 0. An insert of a clinic-B row is rejected by the `WITH CHECK` ("new row violates row-level security policy"), and clinic B still has 0 rows.
- `test_clinic_a_sees_no_clinic_b_rows` checks the same at the SQL level: `SELECT count(*) FROM patient_session WHERE clinic_id = <B>` with `app.clinic_id = <A>` → 0. `test_inserting_a_clinic_b_row_from_clinic_a_fails` gets `DBAPIError` matching "row-level security".
- `test_the_app_role_is_not_privileged`: `careflow_app` has `rolsuper = false` and `rolbypassrls = false`.
- `test_every_clinic_scoped_table_forces_rls` guards future migrations: every table with a `clinic_id` column must have RLS enabled and forced, plus the `clinic_isolation` policy.

## 4. Fail closed: without `app.clinic_id`, `patient_session` returns 0 rows

`test_without_app_clinic_id_nothing_is_visible`: `SELECT count(*) FROM patient_session` as `careflow_app` with no setting → 0, although each clinic has one row. The policy's `NULLIF(current_setting('app.clinic_id', true), '')::uuid` gives NULL, both when the setting is missing and when it is the empty string left by an earlier transaction.

## Contract changes (non-breaking, `make contracts-check`: oasdiff "No breaking changes")

- `Health` now requires `db`, `redis` and `fhir` (new `ComponentStatus`: `ok` | `down`). This adds response fields, which is not breaking for clients.
- `DeviceTokenRequest.device_type` gains `integration`.
- `/v1/nurse/worklist` `x-careflow-roles`: `[nurse, admin]`, as the issue specifies.

## Deviations from the issue text

- **Integration service accounts are `device` rows of kind `integration`**, using `POST /v1/auth/device-token`. The issue lists `device.kind` as kiosk or board, but also needs an integration account per clinic with a secret (ADR-014).
- **Two SELECT-only RLS policies for authentication** (`login_lookup`, `device_token_lookup`). No clinic is known before a token exists, so each lookup sets `app.auth_email` or `app.auth_device_id` in its own transaction, which exposes exactly one row read-only (ADR-014).
- CI builds the image with `docker/build-push-action` (buildx, `type=gha` cache, `load: true`, never pushed) rather than a bare `docker build`.
- Both healthchecks (compose and CI) run `pg_isready -h 127.0.0.1`. Over the Unix socket, Postgres reports ready during its init-script phase and then restarts.
- `/v1/admin/status` reports `ruleset_version: "unreleased"` until the rules engine (M1) ships `RULESET_VERSION`.
- FastAPI's own `/docs` and `/openapi.json` are disabled: `packages/contracts/openapi.yaml` is the contract.
