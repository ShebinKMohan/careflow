## 1. Unit: golden files for each builder; the same record builds a byte-identical Bundle twice

```
$ uv run pytest services/integration/tests/test_writeback_builders.py -q
23 passed
```

- **`test_golden_every_builder[chest_pain|sepsis|routine]`:** every resource from every builder is compared with its golden file: 16 for chest pain, 10 for sepsis and 11 for routine (37 files). The set of golden files must equal the set of resources built.
  - chest pain: Encounter, 8 vital-sign Observations, NEWS2, triage level, the patient's QuestionnaireResponse, Flag, Task, Communication, Provenance;
  - sepsis: no BP, ACVPU or pain; no Task, because the alert has no deadline;
  - routine: no alerts.
- **`test_the_same_record_builds_a_byte_identical_bundle_twice`** (3 records): the canonical JSON bytes are equal (20,762 bytes for chest pain). The golden files also pin the UUIDv5 fullUrls across runs and processes.
- **Targeted tests:**
  - every entry is a conditional create on its own identifier (the Provenance on its tag), and every reference is the EHR patient or another entry;
  - every resource has provenance tags, `subject` and `encounter`;
  - the Encounter is `triaged`, `EMER`, with priority `EM` plus `KTAS-2` (and `AMB` with the default adapter);
  - only the nurse's level is written: the routine override gives level 4, "set by the triage nurse (override)";
  - the vitals use the right codes and attribution: device, nurse or patient;
  - a partial NEWS2 is `preliminary` with the missing inputs;
  - the QuestionnaireResponse holds only what the patient said (no EHR age or sex);
  - one Flag per alert, with the evidence's provenance;
  - the hand-off uses fixed templates and never the patient's words;
  - the Provenance agents and targets are right;
  - no patient, or missing alert evidence, is refused;
  - the transaction-response is read entry by entry (201 and 200, relative and absolute locations; a short response raises).

## 4. `Task.restriction.period.end` equals the alert's `deadline_at`

- **Unit** (`test_the_ecg_task_is_due_at_the_alert_deadline`): `restriction.period.end` is "2026-09-26T09:10:00Z", which is the `CHEST_PAIN_ECG_10MIN` alert's `deadline_at` (arrival 09:00 + 10 min, from the rules engine). The Task is `requested`, `order`, `stat`, code `task-kind#ecg_within_10_min` with the text "12-lead ECG", and `focus` is the Flag. It is `completed` when `completed_actions` holds the action.
- **On HAPI** (in the test of section 2): the stored Task's `restriction.period.end`, parsed, equals `alert.deadline_at`.
- **`complete_task`** then makes a versioned update (`If-Match: W/"1"`). The Task is `completed` at version 2 and keeps its `PATIENT_STATED` tag.

## Deviations from the issue text

- **Encounter class** comes from the hospital adapter (`encounter_class`): `EMER` for `demo_hapi`, as the issue asks, and `AMB` by default, as the mapping table says. The status is `triaged`; both codes were verified and added to the mapping table's log.
- **Encounter priority** holds the ActPriority code (the mapping's convention) followed by the CareFlow `triage-level#<scale>-<level>` coding and a text. That coding is a new mapping entry.
- **More resources than the issue lists, all from the mapping table:**
  - the SpO2 Observation carries LOINC 2708-6 and 59408-5;
  - a triage-level Observation, a pain-score Observation, and one Provenance per write are also written.

  The Provenance, which has no identifier in R4, is matched on the tag `urn:careflow:writeback|<session_id>`.
- **Communication.** It is the one nurse hand-off the issue asks for. The mapping's per-alert notification row now describes it: `about` every Flag, recipient the nurse.
- **Logical references.** Staff and devices are referenced by identifier (`urn:careflow:staff`, `urn:careflow:device`), so CareFlow never creates Practitioner or Device resources in the hospital's record.
- **Outcome statuses.** Besides `ok` and `failed` there is `skipped`, for a patient without an EHR record, where nothing can be written.
- **Status tables.** `fhir_writebacks` holds (session, local id, type, id, version), and the status lives in `fhir_writeback_status`, one row per session.
- **No ECG-done fact.** The contract has none, so `TriageRecord.completed_actions` carries the actions already done. M1-12 fills it from the task route.
- **`complete_task` takes the clinic id**, which RLS needs: `complete_task(clinic_id, session_id, task_id)`.
- **`fhir.write.completed` is an internal event**: a schema in `packages/contracts/events/` and a new `INTERNAL_DATA_MODELS` registry, not a webhook type.
