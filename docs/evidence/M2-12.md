# M2-12: The seven journeys and the three check-in paths (SHE-311)

Status: 28 September 2026. ADR-057. Research prototype; synthetic data only; not for clinical use.

## What changed

- **The shared checks** (`e2e/lib/journey.ts`, `assertJourney`). Every journey checks, in the issue's order:
  - (a) the expected alerts, and no others, on the nurse's open worklist within 2 s of what raised them;
  - (b) the nurse's decision on the card, with the patient and the kiosk refused (403) and a second decision refused (409);
  - (c) the token and room on the board (waiting, then called, never a name) and on the patient's screen;
  - (d) every briefing item with one of the five provenances and a source;
  - (e) the HAPI write-back: one Encounter, the QuestionnaireResponse, the Observations, the briefing's Composition, and a Flag exactly when an alert was raised.
- **New journeys:** `stroke` (with clinic isolation), `no-show`, `checkin-keypad`, `checkin-id-tap`, and `ehr-outage` (HAPI paused mid-visit).
- **Renamed to the issue's names:** `child-drowsy`, `qr-phone` and `checkin-qr`. The existing journeys run on the shared checks.
- **`@ar` variants** of chest pain and routine run fully in Arabic.
- **The no-show's 5-second grace window** (`CAREFLOW_ROOMS_CONFIG`, `e2e/config/rooms.yaml`) is E2E only; a test keeps the shipped 120 s.
- **The CI `e2e` job** runs the whole suite; `workflow_dispatch` with `journeys_only` runs it alone, and failed journeys upload traces and videos.
- **The nightly run.** `scripts/nightly-e2e.sh` writes `eval/reports/e2e_nightly.json`. The LaunchAgent template is `infra/launchd/com.careflow.nightly-e2e.plist`, installed by `make install-nightly`, never loaded.
- **`E2E_RECORD=add`** records only the prompts the cassette lacks and replays the rest. `record` used to re-record every journey's replies.

## Product defects the journeys found, fixed

1. **A briefing document an EHR outage stopped was never written** (`ehr-outage`).
   - **Cause.** The document was written once, at the nurse's decision. With HAPI down, the triage was retried and landed, but the briefing's document never did.
   - **Fix.** The write-back consumer now writes a missing document once the triage is in the EHR, on the triage's terms: pending while the EHR does not answer, dead-lettered when it rejects the document.
   - **Tests.** `test_events_recovery.py` (two tests) and `test_briefing_document.py`.
2. **A late twin write was dead-lettered** (`ehr-outage`, the first runs).
   - **What happened.** A write-back request that HAPI took after the outage landed just as its retry ran. HAPI answered the twin conditional create with 409, the write-back treated that as a rejection, and it dead-lettered the event.
   - **Fix.** A write is retried on 409 too (`WRITE_RETRY_STATUSES`); the next attempt finds what the twin stored.
   - **Test.** `test_writeback_handler.py`.

## The handoff's failure checks

| Check | Where it is proved |
| --- | --- |
| Rules before suggestion; nurse-only final urgency | Every journey (a), (b): no token before the decision; the patient and kiosk get 403, a second decision 409 |
| One token and room assignment | (c): the token is on the board once, the same everywhere; `no-show`: one re-queue, then `no_show` |
| Attributed briefing | (d) in every journey; `chest-pain` also opens the source of the complaint in the doctor's screen |
| Idempotent HAPI writes | (e): one Encounter per session; `ehr-outage`: one after a retried write; `checkin-qr`: a lost answer applied once |
| EHR unavailable | `ehr-outage` (a journey); `services/integration/tests/test_reader.py` (unavailable within budget, partial); `services/api/tests/test_events_recovery.py` (retried until written) |
| Model unavailable | `services/intake/tests/test_extraction.py` (a provider error or timeout is `extraction_incomplete`, and the rules still run); `child-drowsy` taps need no model; the child gets "no model suggestion" |
| Repeated request | `checkin-qr` (a lost response applied once, a stale answer refused); (b) a second decision refused |
| Refresh or restart | `arabic` (kiosk and phone refresh); `consent-voice` (a reload forgets the patient); `checkin-qr` (a lost claim recovered by the same phone) |

## Flaky: the alert budget on a long-lived stack

One local run on a stack that had kept the day's runs (205 sessions on clinic A's worklist) had FAST_STROKE on the worklist 2,704 ms after the answer. The budget is 2 s, asserted locally. The rule fired 284 ms after the answer; the worklist reloads in full on each live alert, and with 205 sessions that load took 330 to 450 ms before rendering. It was not retried. The same suite on a freshly seeded stack had every alert under 725 ms. Recorded in `docs/FLAKY.md` and on SHE-326 (a single-query worklist).
